R-Pingmesh measures the health of RDMA over Converged Ethernet (RoCEv2) fabrics
by probing between every RDMA NIC (RNIC) and reporting latency and loss. It is
a clean-room reimplementation of the system described in the SIGCOMM 2024 paper
by Liu et al. It is not affiliated with the paper's authors. See
[PATENTS.md](PATENTS.md) for related patent information.

This implementation keeps the paper's core measurement design:

- one Unreliable Datagram (UD) queue pair per RNIC, so a single QP can probe
  any peer;
- a 6-timestamp protocol that separates network RTT from host processing
  delay;
- ToR-mesh and inter-ToR pinglists generated by a central controller;
- ECMP path coverage through the IPv6 flow label.

The RDMA data path is a Zig static library; the agent, controller, and
telemetry are written in Go. A per-path SLA analyzer (the paper's "Phase 1"
analysis) runs in the controller. Topology-aware fault localization and the
paper's eBPF-based service tracing are not implemented (see
[Limitations](#limitations)).

## Architecture

```
                        +----------------------+          +---------+
                        |      Controller      |<-------->| rqlite  |
                        | registry, pinglists, |          +---------+
                        | Phase 1 analyzer     |
                        +----------+-----------+
                                   ^  gRPC: RegisterAgent, GetPinglist,
                                   |        ReportProbeAnalysis
              +--------------------+--------------------+
              |                                         |
   +----------+-----------+                  +----------+-----------+
   | Agent (host A)       |                  | Agent (host B)       |
   |  per RNIC:           |                  |  per RNIC:           |
   |   Prober, Responder, |                  |   Prober, Responder, |
   |   ClusterMonitor     |                  |   ClusterMonitor     |
   |  shared: metrics,    |                  |  shared: metrics,    |
   |   analysis reporter  |                  |   analysis reporter  |
   |  librdmabridge (Zig) |                  |  librdmabridge (Zig) |
   +----------+-----------+                  +----------+-----------+
              |          RoCEv2 fabric (UD QPs)         |
              +-----------------------------------------+

   Agents and the analyzer export OTLP metrics to an OpenTelemetry collector.
```

**Controller** (`cmd/controller`, pure Go, `CGO_ENABLED=0`). Stores the RNIC
registry in rqlite, generates pinglists, and runs the Phase 1 analyzer. It needs
no RDMA hardware.

**Agent** (`cmd/agent`, Go with Cgo, `CGO_ENABLED=1`). Runs on every RDMA host.
For each RNIC it opens, it runs:

- a **Responder** that answers probes from other agents;
- a **Prober** that sends probes to the RNIC's targets and matches the ACKs;
- a **ClusterMonitor** that fetches the RNIC's pinglist from the controller.

Every RNIC on a multi-rail host therefore probes on its own behalf. The agent
also runs one OTel metrics exporter, one analysis reporter, and an optional
resource watchdog, all shared across RNICs. It re-registers with the controller
every 60 s as a heartbeat.

**librdmabridge** (`zig/`). A static library that performs every libibverbs
operation: device discovery, QP and CQ setup, CQ polling, and probe
serialization. Go calls it through the C ABI in `zig/include/rdma_bridge.h`.

**Analyzer.** Agents aggregate probe results per path over fixed windows and
send `PathSummary` batches to the controller with `ReportProbeAnalysis`. The
in-process analyzer flags windows whose loss ratio or p99 network RTT exceeds
the configured thresholds, and reports them in logs and OTLP metrics.

## Measurement

### 6-timestamp protocol

Each probe produces six timestamps. The responder sends two ACKs: the first as
soon as the probe arrives, and the second to carry the send time of the first.
The responder's Go goroutine only posts the first ACK; the Zig CQ poller posts
the second as soon as the first ACK's send completion arrives (see
[Responder ACK path](#responder-ack-path)).

```
   Prober                                   Responder
     |  T1  post probe send                     |
     |---------------- probe ------------------>|
     |  T2  probe send completion               |  T3  probe recv completion
     |<--------- first ACK (T1, T3) ------------|
     |  T5  first ACK recv completion           |  T4  first ACK send completion
     |<-------- second ACK (T1, T3, T4) --------|
     |  T6  second ACK processed                |
```

| Timestamp | Taken by | Clock |
|-----------|----------|-------|
| T1 | Prober, in Zig, just before `ibv_post_send` | `CLOCK_MONOTONIC` |
| T2 | Prober NIC, send completion | NIC hardware clock (software fallback) |
| T3 | Responder NIC, receive completion | NIC hardware clock (software fallback) |
| T4 | Responder NIC, first-ACK send completion | NIC hardware clock (software fallback) |
| T5 | Prober NIC, first-ACK receive completion | NIC hardware clock (software fallback) |
| T6 | Prober, in Go, when the second ACK is processed | `CLOCK_MONOTONIC` |

The agent derives three values:

```
NetworkRTT     = (T5 - T2) - (T4 - T3)   // fabric round trip
ResponderDelay =  T4 - T3                // responder processing
ProberDelay    = (T6 - T1) - (T5 - T2)   // prober processing
```

Each difference uses a single clock: T2/T5 and T3/T4 come from one NIC each,
and T1/T6 from the prober host. The two hosts' clocks therefore never need to
be synchronized. A measurement is rejected as invalid when NetworkRTT,
ResponderDelay, or ProberDelay is negative or exceeds a sanity bound
(`internal/probe/probe.go`: 10 s for NetworkRTT, 1 s for the two delays). The
rejection kind is exported as the `kind` attribute of
`rpingmesh.probe_invalid_total`:

| `kind` | Condition | Usual cause |
|--------|-----------|-------------|
| `missing_timestamp` | One of T1–T6 is zero | A bug or a corrupted packet |
| `negative_network_rtt` | `(T5 - T2) < (T4 - T3)` | Software-timestamp jitter, or skew between the two NICs' clock rates |
| `network_rtt_too_large` | NetworkRTT above 10 s | Corrupted timestamps |
| `negative_responder_delay` | `T4 < T3` | Responder timestamps from different clocks |
| `responder_delay_too_large` | ResponderDelay above 1 s | A responder that fell behind its inbound probes: the probe waited more than 1 s before the first ACK was posted |
| `negative_prober_delay` | `(T6 - T1) < (T5 - T2)` | Prober timestamps from different clocks |
| `prober_delay_too_large` | ProberDelay above 1 s | A prober that fell behind its ACKs |

`responder_delay_too_large` points at the responder host, not the network:
NetworkRTT subtracts the responder delay, so with hardware timestamps the
network part of such a probe is still accurate, but the probe is counted as
invalid.

**Hardware timestamps.** When a queue is created, the Zig library requests a
CQ with `IBV_WC_EX_WITH_COMPLETION_TIMESTAMP_WALLCLOCK`. If the provider
returns `EOPNOTSUPP`, it creates the CQ without that flag and takes T2–T5 from
`CLOCK_MONOTONIC` when the poller reads each completion. Software timestamps
include poller latency; soft-RoCE (`rxe`) always uses them. The `Prober
started` and `Responder started` log lines report the mode as
`hw_timestamps`, the agent logs a warning at startup for every queue that uses
software timestamps, and `rpingmesh.agent.hw_timestamps` exports it per queue.

### Wire format

Probes and ACKs share a 40-byte payload serialized explicitly in big-endian
order. Packed structs are avoided so that Zig, C, and Go agree on the layout
without relying on compiler padding rules.

| Offset | Size | Field | Encoding |
|--------|------|-------|----------|
| 0 | 1 | `version` | uint8, currently `1` |
| 1 | 1 | `msg_type` | uint8: `0` probe, `1` ACK |
| 2 | 1 | `ack_type` | uint8: `0` none, `1` first, `2` second |
| 3 | 1 | `flags` | uint8, reserved |
| 4 | 8 | `sequence_num` | uint64 |
| 12 | 8 | `t1` | uint64, nanoseconds |
| 20 | 8 | `t3` | uint64, nanoseconds |
| 28 | 8 | `t4` | uint64, nanoseconds |
| 36 | 4 | reserved | zero |

The format is defined in `zig/src/packet.zig`. A sequence number is a random
32-bit per-process epoch followed by a 32-bit counter, so ACKs for probes sent
before an agent restart cannot match probes sent after it.

## Getting Started

### Prerequisites

| Dependency | Version | Needed for |
|------------|---------|------------|
| Go | 1.27.2+ | Both binaries |
| Zig | 0.17.0 | librdmabridge (the version used in CI and e2e) |
| protoc, protoc-gen-go, protoc-gen-go-grpc | protoc 3.x | gRPC code generation |
| libibverbs-dev, librdmacm-dev | any | Agent build (Linux only) |
| rqlite | 10.x | Controller runtime |

The agent runs only on Linux with an RDMA-capable NIC (for example NVIDIA
ConnectX) or a soft-RoCE (`rxe`) device. The controller runs anywhere.

### Build

Run all commands from the repository root.

```sh
make build              # Zig library, protobuf code, then both binaries
```

The stages can also run individually:

```sh
make build-zig          # zig/zig-out/lib/librdmabridge.a
make generate-proto     # proto/controller_agent/*.pb.go
make build-controller   # bin/rpingmesh-controller
make build-agent        # bin/rpingmesh-agent
make clean              # remove bin/, dist/, and Zig build output
```

The generated protobuf code is not committed, so run `make generate-proto`
before building a binary on its own. `build-agent` also needs
`librdmabridge.a` from `make build-zig`. Both binaries are built for the host
platform; see [Deployment](#deployment) for Linux release builds.

### Run

1. Start rqlite:

   ```sh
   rqlited -node-id 1 ~/rqlite-data
   ```

2. Start the controller:

   ```sh
   ./bin/rpingmesh-controller --config configs/controller.yaml
   ```

3. Start an agent on every RDMA host:

   ```sh
   ./bin/rpingmesh-agent --config configs/agent.yaml \
       --controller-addr controller.example:50051 --tor-id tor-a1
   ```

On startup the agent opens its RDMA devices, creates one UD QP per device for
each of the Prober and Responder, registers its RNICs with the controller,
fetches each RNIC's pinglists, and starts probing and exporting metrics.

Without RDMA hardware, create a soft-RoCE device first:

```sh
sudo rdma link add rxe0 type rxe netdev eth0
```

## Configuration

Both binaries read YAML through Viper. The precedence, from highest to lowest,
is: CLI flag, environment variable, configuration file, built-in default.

- **File.** `--config <path>` loads that file and fails if it is missing.
  Without `--config`, the binary looks for `agent.yaml` or `controller.yaml` in
  `.`, `$HOME/.rpingmesh`, and `/etc/rpingmesh`, and runs on defaults if none
  exists.
- **Environment.** Prefix the key with `RPINGMESH_` and upper-case it, for
  example `RPINGMESH_CONTROLLER_ADDR=controller.example:50051` or
  `RPINGMESH_LOG_LEVEL=debug`.
- **Flags.** Most scalar keys have a flag with hyphens instead of underscores,
  for example `--probe-interval-ms`. Run a binary with `--help` for the list.
- **Lists.** A list key (`allowed_device_names`, `excluded_gid_cidrs`, ...) is a
  YAML sequence in the file, whitespace-separated in an environment variable
  (`RPINGMESH_EXCLUDED_DEVICE_NAMES="mlx5_3 mlx5_8"`), and comma-separated on
  the command line (`--excluded-device-names mlx5_3,mlx5_8`).

Both binaries validate the configuration at startup and exit with an error that
names the first invalid key. The commented defaults are in
[`configs/agent.yaml`](configs/agent.yaml) and
[`configs/controller.yaml`](configs/controller.yaml).

### Agent

**Identity and topology**

| Key | Default | Description |
|-----|---------|-------------|
| `agent_id` | hostname | Agent identifier |
| `hostname` | `os.Hostname()` | Hostname reported for each RNIC |
| `tor_id` | `""` | ToR switch of the host's RNICs. Empty places them in one shared, untagged virtual rack. `unspecified` is reserved and rejected |
| `device_tor_ids` | `{}` | Per-device ToR (`mlx5_0: leaf-a`) for multi-rail hosts whose RNICs connect to different leaf switches |
| `plane_id` | `""` | Network plane (rail) of the host's RNICs. When set, inter-ToR and untagged pinglists pair an RNIC only with RNICs of the same plane |
| `device_plane_ids` | `{}` | Per-device plane, with the same rules as `device_tor_ids` |
| `lldp_tor_discovery` | `false` | Derive each device's ToR at startup from the LLDP neighbor of its netdev |
| `lldp_tor_id_field` | `system_name` | LLDP attribute used as the ToR ID: `system_name` or `chassis_id` |
| `lldpcli_path` | `lldpcli` | lldpd client binary |
| `lldp_discovery_timeout_sec` | `60` | Startup wait for every device to report a neighbor; `0` queries once |

A device's ToR comes from its `device_tor_ids` entry, then from LLDP (when
enabled), then from `tor_id`. A device's plane comes from its
`device_plane_ids` entry, then from `plane_id`. Device names match
case-insensitively, and map values must not be empty. Name the plane after the
largest set of mutually reachable RNICs (the rail), not after a leaf switch.

LLDP discovery runs `lldpcli -f json0 show neighbors` once at startup, so
restart the agent after re-cabling. It needs a running `lldpd` and access to
its socket (root or lldpd's group). lldpd learns a neighbor only from the
switch's next LLDP frame, which is why startup waits up to
`lldp_discovery_timeout_sec`. A device without a neighbor falls back to
`tor_id` with a warning.

See [ToR mapping on multi-rail hosts](docs/design/multi-rail-tor-mapping.md)
for how to choose these values and for the tools in `scripts/topology/`.

**Probing**

| Key | Default | Description |
|-----|---------|-------------|
| `controller_addr` | `localhost:50051` | Controller gRPC address |
| `probe_interval_ms` | `500` | Minimum interval between two probes to the same target (a per-target rate ceiling of `1000 / probe_interval_ms` probes/s) |
| `target_probe_rate_per_second` | `10` | Uniform per-target rate cap; the fallback for a per-type cap left at `0` |
| `tor_mesh_probe_rate_per_second` | `0` | Per-target rate cap for ToR-mesh targets (`0` inherits the uniform cap) |
| `inter_tor_probe_rate_per_second` | `0` | Per-target rate cap for inter-ToR targets (`0` inherits the uniform cap) |
| `pinglist_update_interval_sec` | `300` | Regular pinglist refresh interval |
| `flow_label_rotation_period_sec` | `3600` | Period after which the rotating 20% of each target's flow labels changes |

The built-in per-type caps inherit the uniform cap, so a configuration that
sets only `target_probe_rate_per_second` keeps one rate for every target. The
shipped `configs/agent.yaml` sets the paper's differentiated caps instead:
10 probes/s per ToR-mesh target and 1 probe/s per inter-ToR target. A cap
applies per target; the target's flow labels share it. The probe interval
also limits the rate, so with the shipped 500 ms interval ToR-mesh targets
get 2 probes/s; see
[Per-pinglist-type probe rates](#per-pinglist-type-probe-rates).

Besides the regular refresh, the ClusterMonitor refreshes early when a
pinglist comes back empty or when every probe to a target keeps timing out
(for example, a restarted peer with a new QPN). Early refreshes back off from
30 s up to `pinglist_update_interval_sec`.

**RDMA**

| Key | Default | Description |
|-----|---------|-------------|
| `gid_index` | `0` | GID table index (0–255) |
| `service_level` | `0` | Service Level (PFC priority, 0–7) of every address handle; does not select the queue with `trust dscp` |
| `traffic_class` | `0` | GRH traffic class (0–255) of every address handle: DSCP in the upper 6 bits, ECN in the lower 2 |
| `cq_poll_mode` | `auto` | `event`, `busy`, or `auto`; see [Event-driven completion handling](#event-driven-completion-handling) |
| `event_ring_capacity` | `1024` | Completion events each prober and responder [event ring](#event-delivery-through-an-spsc-ring) holds: a power of two from 64 to 65536, 80 bytes per event, two rings per device. Beyond about one second of inbound probes a larger ring buys little, because a probe answered more than 1 s after it arrived is rejected as `responder_delay_too_large` instead of timing out |
| `allowed_device_names` | `[]` | Devices to open; empty opens all |
| `excluded_device_names` | `[]` | Devices never to open. A device in both lists is a configuration error |
| `excluded_gid_cidrs` | `[]` | Networks (`10.0.0.0/24`) whose devices are never used, matched against each device's GID at `gid_index` |
| `mapped_devices_only` | `false` | Use only the devices listed in `device_tor_ids`; requires a non-empty `device_tor_ids` |

The right `gid_index` depends on the device. Many NVIDIA NICs place a RoCE v1
entry at index 0 and the RoCE v2 entry at a higher index; check with
`ibv_devinfo -d <dev> -v`. Validation rejects only values outside 0–255. If the
index does not resolve to a usable GID on a device, the agent exits with an
error that names the device, port, and GID table size.

Kernel RDMA device names (`mlx5_N`, `mlx5_bond_N`) follow driver probe order
and RoCE LAG state, so they can change across reboots. A bond's RDMA device,
for example, can register as a plain `mlx5_N` before RoCE LAG forms and be
replaced by `mlx5_bond_0` later. Two options select devices without relying on
names alone:

- `excluded_gid_cidrs` skips a device whose GID (RoCE v2 IPv4-mapped GIDs
  match IPv4 networks) lies in a listed network, such as the management
  network. The device is opened to read its GID and closed before any queue is
  created; it is logged at info level with its name, netdev, and GID.
- `mapped_devices_only` skips every device without a `device_tor_ids` entry
  and logs it at warn level. Without it, such a device falls back to `tor_id`;
  when `device_tor_ids` is set, the agent warns about that fallback.

The agent also checks every 5 s the uverbs node of each opened device
(`/sys/class/infiniband_verbs/uverbsN`). If the node disappears or is
re-created (RoCE LAG change, NIC reset, driver reload, hot unplug), or the
device is renamed, the agent logs it, shuts down, and exits non-zero, so
systemd (`Restart=on-failure`) restarts it with the current devices. A rename
leaves the device working, but the device filters, `device_tor_ids`,
`device_plane_ids`, and the `source_rdma_device` label are keyed by name.
The kernel deletes the uverbs node before it waits for open contexts to
close, so this also releases a removal that waits for the agent (drivers
without context disassociation, such as rxe). Devices without a uverbs node
in sysfs at startup are not checked.

To choose `service_level` and `traffic_class`, see
[Choosing `traffic_class` and `service_level`](#choosing-traffic_class-and-service_level).

### Choosing `traffic_class` and `service_level`

Probes observe what a workload (for example, NCCL collectives) observes only
if they travel in the same switch and NIC priority queue. A probe in another
priority does not see that queue's PFC pauses, queueing, or loss. With the
defaults (`traffic_class: 0`, `service_level: 0`), probes usually land in a
lossy default queue even when the workload uses a lossless one. In a lossless
queue, probes see pause-induced latency rather than congestion drops.

Before choosing values:

- DSCP selects the queue only for RoCE v2, because DSCP is carried in the IP
  header. Make sure `gid_index` points at a RoCE v2 GID; index 0 is often the
  RoCE v1 entry.
- Use identical values on every agent. A responder sends its ACKs through
  address handles built from its own `traffic_class` and `service_level`, so
  mismatched values put probes and ACKs in different queues.
- The values apply to the whole agent and take effect only after a restart.

**1. Do not rely on the workload's configuration.** NCCL often runs in user
containers, where `NCCL_IB_TC` and `NCCL_IB_SL` may be set in the image, the
job script, or the container's `/etc/nccl.conf`, none of which the host can
see. If nothing sets it, NCCL uses traffic class `0` unless the communicator
configures one. Newer NCCL versions also have `NCCL_IB_FIFO_TC` for control
messages, which follows `NCCL_IB_TC` by default. NCCL does not use the RDMA
CM, so the RDMA CM `default_roce_tos` setting does not affect it.

**2. Check for a NIC-level override.** NVIDIA's MLNX_OFED/DOCA mlx5 driver can
force a traffic class, shown in
`/sys/class/infiniband/<dev>/tc/<port>/traffic_class` (for example
`Global tclass=106`); inbox drivers may not expose this file. When it is set,
the workload effectively uses that class. NVIDIA documents the override for
RC QPs, whereas R-Pingmesh probes are UD and set the traffic class per address
handle (rdma-core's mlx5 provider copies it into the UD address vector). The
driver source applies the override only to connected QPs, but whether it also
applies to UD on the wire
[has not been verified](https://github.com/yuuki/rpingmesh/issues/71)
([runbook](docs/design/ud-tclass-verification.md)), so set `traffic_class`
explicitly to the same value. This also keeps probes in the right queue if the
override is later removed.

**3. Determine the queue empirically.** This works regardless of containers:

- Trust mode (`dscp` or `pcp`), DSCP-to-priority map, and PFC-enabled
  priorities: `mlnx_qos -i <netdev>` (MLNX_OFED), or, where the driver
  supports it, `dcb apptrust show dev <netdev>`,
  `dcb app show dev <netdev> dscp-prio`, and
  `dcb pfc show dev <netdev> prio-pfc`.
- Per-priority byte counters, sampled twice while jobs run:
  `ethtool -S <netdev> | grep -E '(rx|tx)_prio[0-7]_bytes'`. They count all
  traffic in a priority, not only RoCE.
- Per-priority PFC pause counters (for example `(rx|tx)_prio<N>_pause`) are
  only a hint: they move only under congestion, so an idle counter does not
  prove that a priority is unused.

`scripts/topology/collect_qos_facts.py` collects these facts for each RDMA
port, together with the override from step 2 and the RoCE v2 GID indices, and
prints one JSON object per host. It needs no privileges and changes nothing.
Run it on every host while jobs run, then summarize the results in one place:

```sh
python3 scripts/topology/collect_qos_facts.py --interval 5 > qos-$(hostname -s).json
python3 scripts/topology/summarize_qos_facts.py qos-*.json   # add --json for tooling
```

The summary lists the PFC-enabled priorities and the DSCPs that map to them,
candidate `traffic_class` values, and the busiest priority. It also lists
every port whose trust mode, PFC priorities, DSCP map, or override differs
from the majority. It only suggests values and changes no configuration.

**4. Map the queue to configuration values.**

- `traffic_class` is `DSCP << 2` plus the two ECN bits, for a DSCP that maps
  to the workload's priority. For DSCP 26, `104` is Not-ECT and `106` is
  ECT(0). Where a queue uses WRED/ECN, Not-ECT packets may be dropped where
  ECT packets would be CE-marked. Prefer the value the workload emits on the
  wire (for example an override value such as `106`), and verify the observed
  ECN bits instead of assuming how the NIC sets them.
- `service_level` does not select the queue with `trust dscp`, which is typical
  for RoCE v2 without VLANs; leave it at `0`. Only with `trust pcp` and
  VLAN-tagged RoCE does SL map to the PCP; then use the lossless priority.
- Confirm with the network team that switches classify the chosen DSCP into
  the same queue and do not re-mark it.

**5. Overhead.** Each probe causes three packets (the probe and two ACKs),
each with a 40-byte payload, or about 110 bytes on the wire including
Ethernet, IP, UDP, BTH, DETH, and ICRC headers. A target receives at most
`min(1000 / probe_interval_ms, per-target cap for its type)` probes per
second, shared by its flow labels; at the default 500 ms interval that is at
most 2 probes/s, or about
6 packets/s per target across both directions. An RNIC sends this for each of
its targets and also answers every peer that targets it, so its load is about
`targets × 6` packets/s, which is negligible next to line rate and PFC buffer
capacity.

**Pitfall.** If the workload's traffic class comes from per-device setup,
such as the override above, that misses some RNICs (for example after devices
are renamed), traffic on those rails silently falls back to the default
class. Compare the override, and the probes' `traffic_class`, across hosts and
devices; `summarize_qos_facts.py` reports such ports as override outliers.

### TLS

Controller–agent gRPC is plaintext by default, and both binaries log a warning
at startup in that mode. Set the same `tls_mode` on both sides to enable
transport security:

| Mode | Controller needs | Agent needs | Authentication |
|------|------------------|-------------|----------------|
| `tls` | `tls_cert_file`, `tls_key_file` | `tls_ca_file` | Agent verifies the controller |
| `mtls` | `tls_cert_file`, `tls_key_file`, `tls_ca_file` | `tls_cert_file`, `tls_key_file`, `tls_ca_file` | Both sides verify each other |

### Self-protection

With `self_protection_enabled: true`, a watchdog samples the agent's memory
(`runtime/metrics`, the same accounting as `GOMEMLIMIT`) and CPU time
(`getrusage`) every `watchdog_interval_sec`. While either resource is above its
threshold, the watchdog moves a probe-rate multiplier one step per interval
down the ladder `1.0 → 0.5 → 0.25 → 0.1`, and moves it back up once usage
drops below 75% of the threshold. The multiplier scales every Prober's
per-target caps.

- Memory throttling starts at `throttle_memory_ratio × max_memory_mb` and is
  active only when `max_memory_mb > 0`.
- CPU throttling starts at `throttle_cpu_percent` of the cores the process may
  use (`GOMAXPROCS`).

The multiplier never reaches 0: an agent that stops probing would create a
monitoring blind spot, so self-protection slows probing but never stops it.
The agent logs a warning when throttling starts and when it fully recovers,
and exports the multiplier as `rpingmesh.agent.self_throttle`.

## Deployment

### CPU budget

The agent's CPU use scales with the probe rate it sends and the probe rate it
answers. Per probe answered, the responder handles one receive completion and
two send completions in its CQ poller thread, one ring event and one Cgo call
in Go, and one address-handle creation. Per probe sent, the prober also
spin-waits in Zig for the probe's send completion. In event mode an idle
queue costs no CPU; in busy mode each queue costs about 1% of a CPU even when
idle. Measure the agent's usage at the peak probe rate of your fabric (every
host answers the probes of all its ToR-mesh and inter-ToR peers) and size any
limit from that.

When the agent runs under a CPU limit such as a systemd `CPUQuota`, the kernel
stops every agent thread, CQ pollers included, for the rest of the scheduling
period (100 ms by default) once the quota is used up. Inbound probes then wait
in the responder's event ring. A probe answered more than 1 s after it arrived
is rejected as `invalid_rtt` (kind `responder_delay_too_large`), and once the
ring is full, further probes are dropped and time out at the prober. Both
show up on the probers that target the host, not on the host itself. Leave
headroom above the measured peak, and watch for these signs that the limit
is too low:

- `rpingmesh.event_ring_occupancy_max{ring="responder"}` approaching
  `rpingmesh.event_ring_capacity`, then `rpingmesh.event_ring_dropped_total`
  rising, on the host.
- `rpingmesh.probe_invalid_total{kind="responder_delay_too_large"}` (or the
  `rpingmesh.target_rnic.` variant, which names the host) on its peers.
- `nr_throttled` growing in the agent's cgroup `cpu.stat`.

Self-protection (`throttle_cpu_percent`) reduces only the probes the agent
sends, not the probes it answers.


### Packages

`make package` builds `.deb` and `.rpm` packages for both binaries into
`dist/` (it requires [nfpm](https://nfpm.goreleaser.com/install/)).
`package-agent` and `package-controller` build one of them, and `make archive`
builds binary-only `.tar.gz` archives. The version defaults to the tag on
`HEAD`, or `0.0.0+git.<short sha>`; override it with `VERSION=1.2.3`.

Packaging always builds Linux binaries for `NFPM_ARCH` (the Go host
architecture by default). The controller cross-compiles from any host. The
agent links libibverbs through Cgo, so build it on a matching Linux host, or
inside an Enterprise Linux 9 container with `AGENT_BUILDER=el9` (requires
Docker with buildx). The EL9 build needs only glibc 2.34 or later at runtime,
so it runs on RHEL 9-family hosts as well as Debian 12+ and Ubuntu 22.04+. A
native build inherits the build host's glibc.

Each package installs:

- the binary in `/usr/bin/`;
- a systemd unit in `/usr/lib/systemd/system/`;
- a sample configuration at `/etc/rpingmesh/{agent,controller}.yaml.example`.

Its post-install script creates the `rpingmesh` system user, adds it to the
`rdma` group (agent package only), and reloads systemd. It does not enable or
start the service. Copy the sample to
`agent.yaml` or `controller.yaml`, set at least `controller_addr` on agents,
then enable the service:

```sh
sudo systemctl enable --now rpingmesh-agent.service   # or rpingmesh-controller.service
```

The agent package depends on `libibverbs` and `librdmacm`. The host operator
remains responsible for the RDMA device and for access to `/dev/infiniband/*`.

### GitHub Releases

Each release tag publishes Linux/amd64 packages and archives for both binaries,

### Manual installation

Build Linux binaries with `make package-build-controller` and
`make package-build-agent` (or `make package-build-agent-el9`). The plain
`build-*` targets produce binaries for the build host's platform. Then, on the
target host:

```sh
# Binary, unit, and configuration (shown for the controller; the agent is analogous).
sudo install -m 0755 bin/rpingmesh-controller /usr/bin/
sudo install -m 0644 packaging/systemd/rpingmesh-controller.service /usr/lib/systemd/system/
sudo install -D -m 0644 configs/controller.yaml /etc/rpingmesh/controller.yaml

# Service account expected by the units.
sudo groupadd --system rpingmesh
sudo useradd --system --no-create-home --shell /usr/sbin/nologin --gid rpingmesh rpingmesh

# Agent hosts only: the unit runs with SupplementaryGroups=rdma, and systemd
# refuses to start it if that group does not exist.
sudo groupadd --system rdma 2>/dev/null || true
sudo usermod -a -G rdma rpingmesh

sudo systemctl daemon-reload
sudo systemctl enable --now rpingmesh-controller.service
```

The agent unit grants only `CAP_IPC_LOCK` with `LimitMEMLOCK=infinity`, which
memory registration needs. The comments in
`packaging/systemd/rpingmesh-agent.service` explain why it does not grant
`CAP_NET_RAW`. If you enable LLDP discovery, also give the `rpingmesh` user
access to lldpd's socket.

### Running rqlite on the controller host

The controller unit starts after `rqlite.service` and wants it. `rqlited`
accepts connections before its store is open, so a `Type=simple` rqlite unit
can still let the controller start too early. The controller then logs
`rqlite not ready; retrying` and retries for `database_connect_timeout_sec`
before exiting. To order the start exactly, make rqlite report readiness only
once `/readyz` succeeds:

```ini
# /etc/systemd/system/rqlite.service.d/readyz.conf
[Service]
ExecStartPost=/bin/sh -c 'for i in $(seq 1 120); do curl -fsS -o /dev/null http://127.0.0.1:4001/readyz && exit 0; sleep 1; done; exit 1'
TimeoutStartSec=150
```

### Upgrading

Upgrade the controller before the agents. An older controller does not
understand per-device ToRs or planes: agents that set `device_tor_ids` log an
error and fall back to `tor_id` for every device, and agents that set a plane
log a warning while the controller ignores it.

Releases that made `tor_id` optional also need the following care:

- Before upgrading the controller, rename any ToR literally named
  `unspecified`. The new controller rejects heartbeats that carry it, and its
  metric series would merge with those of untagged RNICs.
- Older agents export an empty `source_tor`/`target_tor` until they are
  upgraded. The controller relabels empty ToRs when it ingests `PathSummary`
  reports, but only the new agent (or collector-side relabeling) fixes the
  probe metrics.
- Rolling back to an older controller rejects an empty `tor_id` again and
  removes the cap on the untagged mesh. Heartbeat failures do not stop
  probing, so stop untagged agents, or delete their registry rows, before
  rolling back.

- `reason` (on `probe_failed_total` only): `timeout`, `send_error`,

- `kind` (on `probe_invalid_total` only): one of the seven rejection kinds.

Analyzer metrics, exported by the controller with
`service.name=rpingmesh-analyzer`:

| Metric | Type | Attributes | Description |
|--------|------|-----------|-------------|
| `rpingmesh.analyzer.path_summaries_total` | Counter | — | Ingested per-path window summaries |
| `rpingmesh.analyzer.sla_violations_total` | Counter | `source_tor`, `target_tor`, `kind` (`loss`, `rtt`) | Detected SLA violations |

By default no metric carries a GID or any other identity of the destination
RNIC, because a fabric with thousands of RNICs would produce an unbounded number
of series. Per-probe detail, including GIDs, flow labels, and all six
timestamps, is logged at `debug` level instead.

`metrics_target_rnic_labels` opts in to per-destination-RNIC metrics, which
localize loss or latency to one remote RNIC. They are separate instruments
with the prefix `rpingmesh.target_rnic.`, carrying the default attributes
plus `target_hostname`, `target_rdma_device`, and `target_netdev`
(`unspecified` when unknown). The default metrics above are recorded exactly
as before, so the bundled dashboards and alerts are unaffected.

- `counters` exports `rpingmesh.target_rnic.probe_total`,
  `probe_success_total`, `probe_failed_total` (with `reason`), and
  `probe_invalid_total` (with `kind`), which is enough to find the RNIC behind
  a loss or a burst of invalid measurements.
- `all` also exports `rpingmesh.target_rnic.network_rtt_ns`,
  `prober_delay_ns`, and `responder_delay_ns`. Each label set costs about 50
  histogram series, so use it on small fabrics or for a time-boxed
  investigation.
- With the default `metrics_target_rnic_labels_scope: stable`, sampled targets
  carry `_sampled` in all three labels. The controller marks a target as
  sampled (`PingTarget.sampled`) when it re-picks it at random on every
  pinglist refresh: every inter-ToR target, and every target of an untagged
  ToR-mesh larger than `unspecified_mesh_max_targets`. The OTel SDK keeps every
  attribute set it has seen, so labelling them would grow the series count
  over time. An older controller does not set the flag; the agent still
  treats inter-ToR targets as sampled, but a capped untagged mesh is labelled.
  Whether an untagged mesh is sampled is decided on each refresh, so a mesh
  whose size crosses `unspecified_mesh_max_targets` switches its targets
  between their identity and `_sampled`, leaving both sets of series.
- Series are never removed while the agent runs: a target that leaves (a
  replaced host, a renamed netdev) keeps its series until the agent restarts.
- The OTel SDK caps each instrument at 2000 attribute sets per agent by
  default. `metrics_cardinality_limit` can only raise it, because the SDK
  applies one limit to every instrument, including the default ones. When a
  `target_rnic` instrument reaches the cap, further label sets fold into its
  `otel.metric.overflow="true"` series. Because the instruments are separate,
  the default metrics never overflow because of the destination labels. Query
  `{otel_metric_overflow="true"}` to detect it.
- `target_netdev` needs a controller and target agents that report netdevs
  (this release or later); otherwise it is `unspecified`. Upgrade every
  controller before enabling the option: an older controller sharing the
  rqlite database rewrites the RNIC rows it re-registers without the netdev,
  so the label would alternate between the netdev and `unspecified`.

"Estimating the series count" in
[`docs/design/grafana-dashboards.md`](docs/design/grafana-dashboards.md) shows
how to size the metric volume.

The RTT histograms use these bucket boundaries in nanoseconds. They are dense

### Logs

Both binaries log to stderr through zerolog, either human-readable
(`log_format: console`) or as one JSON object per line (`log_format: json`).
`scripts/topology/rtt_tor_check.py` reads the JSON form. The JSON field names
are stable but differ by binary: the agent uses snake_case keys (`agent_id`,
`source_tor`), the controller camelCase ones (`listenAddr`, `requesterGID`). Per-probe detail is
logged only at `debug` level; its `Probe result recorded` line carries
`invalid_kind` and `validation_error` for a rejected measurement.

Rejected measurements are also logged at `warn` level, at most once every
10 s, with the kind, the validation error, all six timestamps, the three
derived values, the target host and device, and the number of rejections
suppressed since the previous line. The full count is on
`rpingmesh.probe_invalid_total`. A responder logs a warning, at most every
10 s, when ACK pairs failed after it posted them (a send completion error, or
a second ACK the CQ poller could not post); the prober sees each of them as a
timeout.

## Design Notes

### Zig for the RDMA data path

All libibverbs calls, CQ polling, buffer management, and probe serialization
are in Zig. The data path therefore runs on its own threads, outside the Go
scheduler and garbage collector, and Zig checks struct layout and alignment at
compile time. C bindings are generated from `zig/src/c.h` by the build's
TranslateC step. The library is built as `zig/zig-out/lib/librdmabridge.a` and
linked into the agent through Cgo.

### Event delivery through an SPSC ring

Completions travel from the Zig CQ poller thread to Go through a lock-free
single-producer, single-consumer ring buffer with cache-line-padded atomic
head and tail indices. Go drains the ring by calling
`rdma_event_ring_poll()`; Zig never calls back into Go. This avoids running Go
code on a foreign thread and avoids one Cgo transition per completion. Because
a queue writes into its ring, the ring is created before the queue.

### Event-driven completion handling

The agent should cost almost no CPU on the hosts it monitors, so in event mode
neither side of the ring polls on a timer:

- **Zig CQ poller.** Each CQ is attached to a completion channel. The poller
  arms the CQ (`ibv_req_notify_cq`), drains it, and sleeps in `poll()` until
  the next completion event. Arming before draining guarantees that a
  completion racing with the final empty poll still raises an event. A 100 ms
  `poll()` timeout re-arms and drains as a safety net.
- **Go consumer.** Each ring owns an `eventfd` that the poller signals after
  draining a batch that produced events. The Go consumer waits on a duplicate
  of that descriptor through the runtime netpoller, so a waiting consumer is a
  parked goroutine rather than a blocked thread.

In busy mode, the poller sleeps about 50 µs between CQ polls and the Go
consumer polls the ring every 100 µs, which costs roughly 3% of a CPU per RDMA
device. Busy mode is also the fallback when a provider cannot create a
completion channel or arm the CQ.

With hardware timestamps, the poller's wake-up time does not affect T2–T5, so
event mode does not change the measured NetworkRTT. Software timestamps are
taken when the poller reads a completion, so wake-up latency becomes
measurement error. `cq_poll_mode: auto` therefore uses event mode with hardware
timestamps and busy mode with software timestamps. The `Prober started` and
`Responder started` log lines report the mode in effect as `cq_events`.

### Responder ACK path

The second ACK carries T4, the send completion time of the first ACK, so it
cannot be sent before that completion arrives. The responder does not wait for
it. For each probe, the Go goroutine calls `rdma_send_ack_pair()`, which
serializes both ACKs into one send slot (T4 still zero in the second), creates
one address handle, posts the first ACK, and returns. When the CQ poller
reads that ACK's send completion, it writes the completion timestamp into the
staged second ACK and posts it on the same slot and address handle, after the
current CQ poll ends. The second ACK's completion frees the slot.

The goroutine that drains the responder's event ring therefore never blocks on
a send completion and never spins while one is outstanding: the ring drains at
the inbound probe rate, and a late completion delays only its own probe. Up to
32 ACK pairs (the queue's send slots) can be in flight. When all of them are,
the goroutine retries for up to 1 s before giving up on the probe.

T4 is the same timestamp as before: the NIC's send completion time of the
first ACK, or with software timestamps the time the CQ poller read that
completion. Probes still use the synchronous path: the prober waits for each
probe's send completion to read T2.

### Address handles

Address handles are created with `ibv_create_ah()` rather than
`rdma_create_ah()`, which requires an RDMA CM connection context that UD
probing does not need. The data path does not use the RDMA CM.

### ECMP path coverage with flow labels

RoCEv2 UD does not let the sender choose the UDP source port, so the probes
select ECMP paths through the IPv6 flow label in `ibv_ah_attr.grh`. The
`source_port` field of `PingTarget` is informational only. The Zig library
creates an address handle for every send, so each probe can use a different
flow label.

A single flow label per target would always exercise the same ECMP path and
miss drops on the others. The controller therefore sizes a set of `n` labels
per target. If each probe picks one of `m` equally likely paths, a given path
is missed by `n` probes with probability `((m-1)/m)^n`. Treating the paths as
independent, all `m` paths are covered with probability at least `p` when

```
n = ceil( ln(1 - p^(1/m)) / ln((m-1)/m) )
```

This is Eq. (1) of the paper. The independence assumption makes `n` slightly
optimistic; the union bound `1 - m·((m-1)/m)^n ≥ p` gives the conservative
value. At the defaults (`m = 16`, `p = 0.9`) the two give 78 and 79 labels,
and the `ecmp_max_flow_labels` cap of 64 applies to both.

The controller stamps `flow_label_count = n` and a 32-bit `flow_label_seed`
into every `PingTarget`. The agent derives label `i` from a hash of the seed
and `i`, masked to 20 bits, and cycles through the labels round-robin. Every
fifth label index also mixes in the rotation epoch (`floor(unix_time /
flow_label_rotation_period_sec)`), so about 20% of the labels change each
period while the rest stay stable for time-series continuity. Wall-clock time
only selects labels and never enters a measurement. When `flow_label_count` is
0 or 1, the agent uses the legacy `flow_label` field unchanged.

The flow label of each probe appears in debug logs but never as a metric
attribute.

### Per-pinglist-type probe rates

The controller stamps `pinglist_type` (ToR-mesh or inter-ToR) into every
`PingTarget`. Each Prober keeps one rate limiter per type, with an aggregate
rate of the effective per-target rate below times the number of targets of
that type, recomputed on every pinglist update.

Each target is probed at

```
min(1000 / probe_interval_ms, per-target cap for its type) × throttle multiplier
```

probes per second. `probe_interval_ms` is a ceiling: a target never gets more
than one probe per interval, so a cap has an effect only below
`1000 / probe_interval_ms` (2 probes/s at the default). When a per-type cap
and `target_probe_rate_per_second` are both `0`, the interval is the only
limit. The self-protection multiplier scales this
effective rate, so a throttle slows probing even when the cap is above the
ceiling.

The Prober paces the two types independently: one goroutine interleaves them
and always sends the probe whose type is due first, with sends spread evenly
over each type's period. A binding cap on one type therefore does not slow
the other. Sends stay on one goroutine because the RDMA send path waits for
its completion through a single per-queue slot.

With the shipped configuration (500 ms interval, caps 10 and 1), ToR-mesh
targets get 2 probes/s and inter-ToR targets 1 probe/s. To reach the paper's
10:1 ratio, set `probe_interval_ms: 100`; this raises ToR-mesh probe traffic
fivefold, so check it against the overhead estimate in
[Choosing `traffic_class` and `service_level`](#choosing-traffic_class-and-service_level) first.

### Staleness in the registry

The rqlite `rnics` table records each RNIC's last registration as
`last_updated_epoch INTEGER` (Unix seconds). The controller stamps the value
and computes the active and stale cut-offs from its own clock, and binds them
as query parameters, so the checks are integer comparisons that can use an
index. SQLite's `'now'` is avoided because rqlite rewrites it in write
statements using the server's local time zone, which shifts it on a non-UTC
host.

## Development

### Tests

```sh
make test           # Go tests of every pure-Go package (no Cgo, no RDMA hardware)
make test-zig       # Zig unit tests (needs libibverbs headers, not hardware)
make test-scripts   # Python tests of scripts/topology/ (standard library only)
make vet            # go vet ./...
make test-all       # Zig tests and every Go package except e2e/ (Linux build environment)
```

Run one Go test with `go test -v ./internal/probe/... -run TestCalculateRTT`.

The end-to-end suites run in Docker:

- `make test-e2e-controller` runs the agent-to-controller tests against
  rqlite.
- `make test-e2e` runs the RDMA tests in a privileged container with two
  soft-RoCE devices. It needs the host's `rdma_rxe` kernel module; on macOS,
  run `make setup-colima` once to install it in the Colima VM.

`TestProbeToOTelMetrics` in `make test-e2e` checks the shape of the exported
metrics and tolerates runs in which no probe succeeds. Soft-RoCE in the CI
topology does not complete every probe and ACK exchange, so that test does not
guarantee that the success path runs end to end.

### Changing the Zig library

1. If the C ABI changes, update `zig/include/rdma_bridge.h` first.
2. Edit `zig/src/`, then run `make build-zig`.
3. Update `internal/rdmabridge/bridge.go` to match the header.
4. Run `make build-agent`.

### Adding a gRPC method

1. Edit `proto/controller_agent/controller_agent.proto` and run
   `make generate-proto`.
2. Implement the method in `internal/controller/service.go`.
3. Call it from `internal/agent/controller_client/controller_client.go`.

### Adding a metric

Create the instrument in `NewMetricsCollector` in
`internal/telemetry/otel_metrics.go` and record it from `RecordProbeResult` or
a new method. Use only bounded attributes: ToR IDs and local RNIC names are
acceptable; GIDs and other destination-RNIC identities are not.

## Limitations

- **No fault localization.** The analyzer detects per-path SLA violations but
  does not locate the faulty switch or link (the paper's Phase 2). It keeps
  summaries only in a bounded in-memory window. See
  [the Phase 2 design](docs/design/analyzer-phase2-localization.md).
- **No service tracing.** The paper uses eBPF to follow RDMA QP lifecycles and
  monitor the paths that services actually use. This implementation probes
  only the RNIC mesh. See [the design](docs/design/ebpf-service-tracing.md).
- **No recovery from RNIC failures at runtime.** If a device fails or
  disappears after startup, its Prober and Responder stop working until the
  agent restarts. See [the design](docs/design/rnic-runtime-reinit.md).
- **Inter-ToR targets are a fixed-size sample.** Flow labels are sized for a
  coverage probability, but each inter-ToR pinglist samples a fixed
  `inter_tor_sample_size` remote ToRs.
- **One SL and traffic class per agent.** `service_level` and `traffic_class`
  apply to every address handle on every device; a target cannot use a
  different priority. Soft-RoCE carries these values on the wire but does not
  implement PFC or DSCP queuing, so their effect can be verified only on real
  hardware. See
  [Choosing `traffic_class` and `service_level`](#choosing-traffic_class-and-service_level).
- **Self-protection is coarse.** It reacts only to the agent's own CPU and
  memory use, with static thresholds and a four-step multiplier, and never
  stops probing.
- **Plaintext gRPC by default.** TLS is opt-in, and certificates are not
  reloaded without a restart.
- **No agent container image.** The agent needs Cgo, libibverbs, and access to
  the host's RDMA devices, so it ships as packages and archives only. The
  repository provides `Dockerfile.controller` for the controller and Dockerfiles
  for the test environments.
